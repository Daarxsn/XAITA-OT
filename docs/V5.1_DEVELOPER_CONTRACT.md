# XAITA-OT V5.1 Developer Contract

**Status:** COMPLETE / LOCKED for the V5.1 baseline contract surface.

## Purpose

This document freezes the behavior that the V5 line is required to preserve while later work improves real-dataset validation, productization, performance, security evidence and enterprise integration.

The contract is a compatibility baseline. It does not claim benchmark performance, production OT certification, or customer-specific acceptance.

## Public compatibility identity

| Item | Contract |
|---|---|
| Contract ID | `XAITA-OT-V5-DEV-1.0` |
| V5 phase | `baseline-hardening` |
| Package line | `0.5.x` / V5 |
| Supported Python | 3.10, 3.11, 3.12, 3.13 |
| Safety mode | Analyst-support only |
| Detection/attribution rule | DC remains distinct from AC |
| Evidence rule | Evidence IDs and provenance are preserved |

The executable identity is defined by `xaita_ot.v5.V5_CONTRACT`.

## Canonical analytical pipeline

The public pipeline order is:

**Observation → Detection → Episode → Context → Attribution → Explanation → Risk → CTI**

Stages may be implemented internally by different modules, but downstream changes must not silently remove or reorder these analytical contract stages.

## CLI contract

The public CLI entry point is:

```text
xaita
```

Supported commands in the V5.1 contract:

| Command | Purpose |
|---|---|
| `xaita --version` | Report installed package version |
| `xaita demo` | Execute the built-in deterministic analysis demo |
| `xaita synthetic-data` | Generate deterministic synthetic OT data |
| `xaita validate-data` | Validate researcher-supplied benchmark CSVs and write a reproducibility manifest |
| `xaita real-experiment` | Validate one benchmark CSV, execute one detector, and write an auditable result envelope |

Existing options and output paths are documented by the CLI help surface. New commands or breaking argument changes require contract and regression-test updates.

### Authentication

Protected API routes support the configured API-key/Bearer authentication path. Role levels are:

```text
viewer → analyst → admin
```

Read operations require viewer access; experiment and event-analysis execution requires analyst access. Authentication is optional for local development and must be configured for staging/production according to the deployment preflight.

### Compatibility rules

- Existing V1–V4 request/response behavior must not change silently.
- Additive response fields are preferred over breaking changes.
- Unknown fields on contract-validated request models remain rejected.
- Event and request-size limits remain enforced.
- HTTP errors must retain documented status semantics unless the API contract is intentionally versioned.
- Secrets, credentials and local confidential filesystem content must not be exposed in API responses.

## Research and evidence contract

Every later analytical feature must preserve:

1. Evidence identifiers.
2. Backward provenance links.
3. DC ≠ AC semantics.
4. Explicit uncertainty rather than unvalidated probability claims.
5. Analyst-support-only operational boundary.
6. Reproducibility metadata for benchmark claims.

Synthetic/demo fixtures are implementation-validation inputs only. They must not be presented as real SWaT, BATADAL or TON-IoT benchmark results.

## Product safety boundary

XAITA-OT is an analyst-support security analytics system. It does not issue PLC/RTU/SCADA control commands and does not autonomously perform safety-critical OT actions.

Deployment into a live OT environment requires separate architecture, safety, security and customer acceptance evidence.

## Change control

Any future change that affects this contract must include:

- an explicit compatibility decision;
- unit, integration or acceptance coverage appropriate to the change;
- updated documentation;
- CI evidence on the final commit.

A change may extend the contract, but it must not weaken the safety, provenance or reproducibility invariants.

## Acceptance evidence

The V5 contract is executable through `xaita_ot.v5.V5_CONTRACT` and covered by `tests/test_v5_contract.py`.

The repository's current CI/release gates must remain green before this contract is considered the accepted V5.1 baseline.
