# XAITA-OT V4.2 Productization Baseline Audit

**Branch:** `v4-development`  
**Baseline:** V1–V3 completed engineering baseline  
**Purpose:** Establish the productization gaps that must be closed before organizational handover.

## 1. Confirmed baseline

The current repository already contains:

- Python package metadata in `pyproject.toml`.
- Package name `xaita-ot` and version `0.5.0`.
- Supported Python range `>=3.10,<3.14`.
- CLI entry point `xaita = xaita_ot.cli:main`.
- FastAPI and Uvicorn dependencies.
- `run_api.py` API launcher.
- `Dockerfile` and `docker-compose.yml`.
- `docs/` documentation set.
- CI workflows for Python 3.11 and 3.12.
- V4.1 installation and API smoke verification workflows.

## 2. Productization findings

### Blockers for enterprise handover

1. **Release identity is not yet enterprise-grade.** The package is still versioned `0.5.0`, while the engineering roadmap uses V1–V4 terminology. A formal release/version mapping is required.
2. **License/product status is not finalized.** Package metadata currently describes the license as `Proprietary - research prototype`. Legal ownership, distribution terms, and customer-use terms must be decided before external handover.
3. **Production deployment boundary is not closed.** The README explicitly distinguishes the current analyst-support system from certified or production OT/ICS deployment. V4 must preserve this safety boundary and define the supported deployment claim.
4. **Security acceptance evidence is incomplete.** CI success is not equivalent to a security assessment. SBOM, vulnerability policy, threat model, authentication/RBAC review, secrets handling, and security test evidence are required.
5. **Independent installation and operation evidence is incomplete.** Automated CI validates workflows, but an independent-user handover test and customer-style acceptance record are still required.

### High-priority gaps

- Formal CLI contract: commands, arguments, exit codes, error taxonomy, and stable output schema.
- Formal API contract: request/response schemas, authentication behavior, limits, errors, versioning, and compatibility policy.
- Configuration reference and secure defaults.
- Structured logging and audit-event specification.
- Container hardening and runtime configuration.
- SBOM generation and artifact retention.
- Backup, recovery, upgrade, and rollback procedures.
- Operational runbook and troubleshooting guide.
- Dataset/data-governance policy for customer environments.
- Support, maintenance, vulnerability disclosure, and release policy.

### Medium-priority gaps

- Customer-facing architecture diagram.
- Example deployment profiles.
- Performance/load baseline.
- Observability metrics and alert guidance.
- Report templates for analysts and management.
- Integration examples for SIEM/CTI/SOC workflows.
- Automated documentation checks.

## 3. V4.2 acceptance criteria

V4.2 is complete only when:

- A clean user can install from a versioned artifact.
- CLI commands and exit codes are documented and tested.
- API schemas and error responses are documented and tested.
- Configuration is documented with safe defaults.
- Container execution is reproducible and documented.
- Outputs are versioned, machine-readable, and provenance-preserving.
- SBOM and dependency audit artifacts are generated for the release.
- Security and operational limitations are explicit.
- A user can follow the documentation without developer assistance.
- Existing V1–V3 regression and CI checks remain green.

## 4. Implementation order

1. Lock version/release policy.
2. Define CLI/API contracts.
3. Define configuration and logging contracts.
4. Harden container and runtime defaults.
5. Add SBOM/security artifact generation.
6. Add independent-user acceptance workflow.
7. Produce the V4.2 release candidate and handover evidence.

## 5. Non-goals for V4.2

V4.2 must not claim:

- Certified production OT/ICS safety.
- Autonomous safety-critical control.
- Guaranteed attack detection or attribution.
- Benchmark performance from synthetic/demo fixtures.

Those claims require separate evidence and acceptance gates.

## 6. Decision

The V1–V3 engineering baseline is suitable for continued development. It is **not yet an enterprise handover release**. V4.2 will close the productization, security-evidence, operational-documentation, and independent-acceptance gaps identified above.
