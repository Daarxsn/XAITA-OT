# XAITA-OT V4.3.1 — Security Baseline Audit

## Scope

This baseline reviews the repository's current deployment and runtime entry points before enterprise-readiness hardening.

## Initial findings

### S-001 — Container runs as root

The current `Dockerfile` does not create or switch to a non-root user. The application therefore runs as the default container user.

**Risk:** A process compromise may provide unnecessary container-level privileges.

**Required action:** Add a dedicated unprivileged runtime user and run the application as that user.

### S-002 — Dependency installation is not fully reproducible

The `Dockerfile` upgrades `pip` and installs the package without a pinned lock/constraints workflow.

**Risk:** Builds may change as dependencies are released, reducing reproducibility and complicating vulnerability evidence.

**Required action:** Introduce a controlled constraints/lock strategy and document dependency update policy.

### S-003 — No container health check is declared

The `Dockerfile` exposes port `8080` but does not declare a `HEALTHCHECK` instruction.

**Risk:** Deployment platforms may not have a standard container-level readiness/liveness signal.

**Required action:** Add a health endpoint contract and container health check after confirming the API route.

### S-004 — Runtime binds to all interfaces

`run_api.py` starts Uvicorn on `0.0.0.0:8080`.

**Risk:** This is appropriate for container networking but must be paired with deployment-level network controls, authentication, TLS termination, and restricted exposure.

**Required action:** Document the trusted deployment boundary and ensure production exposure is not unauthenticated.

### S-005 — Environment template is development-only

`.env.example` currently defines `XAITA_ENV=development` and contains no documented production configuration contract.

**Risk:** Operators may lack a clear, safe production configuration baseline.

**Required action:** Document required variables, safe defaults, secret handling, and production configuration validation.

## Acceptance criteria for V4.3.1

- [ ] Runtime image executes as non-root.
- [ ] Dependency versions and update process are reproducible.
- [ ] Health/readiness behavior is documented and tested.
- [ ] Production network exposure and authentication boundary are documented.
- [ ] Production environment variables and secret handling are documented.
- [ ] Security checks run in CI.
- [ ] No real secrets are committed.
