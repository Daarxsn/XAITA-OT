# XAITA-OT V5.1 Baseline Hardening Backlog

**Status:** COMPLETE / LOCKED as the scoped backlog definition.

## Purpose

Translate the remaining productization and research-assurance work into an explicit backlog while keeping the V5.1 compatibility contract stable.

This document defines work to be implemented in subsequent stages. It does not claim that all backlog items are already complete.

## P0 — Research and acceptance blockers

| Work item | Required outcome |
|---|---|
| Real SWaT/BATADAL/TON-IoT validation | Dataset identity, schema validation, chronological/episode-aware split record, seed/config capture and reproducible result artifacts |
| Four-detector real-data execution | Controlled Random Forest, CNN, LSTM and CNN-LSTM execution with bounded resource use |
| End-to-end evidence continuity | Detection → episode → context → attribution → explanation → risk → CTI preserves evidence IDs, provenance, DC/AC separation and uncertainty |

## P1 — Product and engineering hardening

| Work item | Required outcome |
|---|---|
| CLI contract | Stable commands, arguments, exit-code semantics and error taxonomy |
| Configuration contract | Explicit path resolution, environment overrides, secure defaults and deployment reference |
| Execution lifecycle | Job state, duplicate/concurrency protection, timeout/failure semantics for expensive experiments |
| Experiment manifests | Immutable software/config/dataset/seed/split metadata and output hashes |
| Data-driven dashboard | Live API-backed state with demo/static content clearly separated |
| ATT&CK/CTI package | Version-pinned, reviewed mappings and provenance |
| Security evidence | SAST, dependency/container scanning and security-review preparation |
| Enterprise integrations | Explicit SIEM/CTI export and audit-event interoperability contracts |

## P2 — Handover and support

| Work item | Required outcome |
|---|---|
| Recovery and lifecycle operations | Backup, recovery, upgrade, rollback and retention procedures |
| Operations documentation | Runbook, troubleshooting and independent-user acceptance workflow |
| Governance | Dataset/legal/license controls and customer deployment boundaries |
| Product support | Maintenance, support and vulnerability-disclosure process |

## Scope rule

The backlog is intentionally separate from release-governance completion. A green repository CI run demonstrates that the current implementation remains internally consistent; it does not convert a backlog item into external benchmark, security or customer-acceptance evidence.

## Tracking rule

Each backlog item should be closed only after its implementation, tests, documentation and applicable acceptance evidence are present on the final commit.

## Day 19 completion

Day 19 establishes this backlog and the executable developer contract that future implementation must preserve.
